# keyblox 리팩터링

사용자 계정 스킬 saba-refactor를 keyblox 구조에 맞게 옮겼다. 리팩터링은 외부 동작을 그대로 두고 구조만 바꾸는 일이다. 버그 수정·기능 추가와 섞지 않는다. 저장소의 AGENTS.md가 이 문서보다 우선한다.

## 1. 후보 고르기 (분석 요청일 때)

- 근거가 있는 냄새만 후보로 올린다: 같은 값·로직이 두 곳 이상(설정 기본값, 키맵, 상수), OS 무관 모듈(`midi`·`layout`·`schedule`·`analyze`·`ui`)에 섞인 Win32 의존, 재생 스레드 안의 계산, 300줄 넘는 함수, 깊은 중첩, 오류를 삼키는 `unwrap_or_default`/`.ok()`/`let _ =`.
- 후보마다 `file:line`, 문제, 바꾼 뒤 모습, 위험도, 보호 테스트 유무를 적는다.
- 반박 단계를 거친다: "지금 그대로 두면 실제로 무엇이 나빠지는가"에 답하지 못하면 뺀다.
- 결과는 HTML Artifact(artifact-design)로 낸다. 사용자는 휴대폰으로 본다.

## 2. 시작 전

- 대상 코드를 덮는 테스트가 있는지 확인한다. 없으면 현재 동작을 고정하는 특성 테스트를 먼저 쓰고 통과시킨다(구현을 베끼는 테스트 금지). 스케줄러는 같은 곡의 `--dump-acts` 출력(키 입력 타임라인)이 바뀌지 않는지가 좋은 기준이다.
- 사용자에게 보이는 동작(남는 음, 타이밍, 핫키, 화면)이 바뀌면 리팩터링이 아니다. 멈추고 사용자 결정으로 올린다.

## 3. 진행

- 한 번에 한 가지 변형(추출, 이름 변경, 이동, 중복 합치기)만 하고 매번 관련 최소 검사를 돌린다.
- 무관한 파일을 포맷하거나 정리하지 않는다. `cargo fmt`를 크레이트 전체에 돌리지 않는다. 바꾼 줄은 모두 이번 목적에 닿아야 한다. 내 변경으로 안 쓰이게 된 것만 지운다.

## 4. 끝

- 영향 범위 검사를 한 번: `cargo test -q`, Windows 코드에 닿으면 Windows 빌드(CI 또는 `cargo check --target x86_64-pc-windows-gnu`). 실행하지 않은 검사는 통과로 쓰지 않는다.
- `player.rs`·`gui.rs`의 동작에 닿으면 PC 실측 후 병합한다.
- 리뷰는 code-review + simplify + rust-review. PR 설명에 "동작 변경 없음"의 근거(테스트 이름, 타임라인 비교 결과)를 적는다.
- 모듈 역할이 바뀌면 같은 커밋에서 `README.md`의 "폴더 구조"를 고친다.
