# keyblox 심층 감사

사용자 계정 스킬 saba-deep-audit의 방식(진입점 전수 → 체크리스트 → 반박 검증)을 keyblox에 맞게 옮겼다. 바뀐 코드만 보는 리뷰와 정상 흐름만 확인하는 테스트로는 잡히지 않는 버그를 찾는 것이 목표다.

## 언제 쓰나
- 릴리스를 자르기 전에 부분마다 한 번씩 돌린다.
- 사용자가 특정 부분의 검토를 요청했을 때.
- 일반 PR 리뷰에서는 아래 체크리스트만 바뀐 코드에 적용한다.

## 진행 방법
1. 범위를 하나 고른다: 재생 엔진(`player.rs`), GUI 셸(`gui.rs`), 화면(`ui.rs`), 스케줄러(`schedule.rs`·`layout.rs`), MIDI(`midi.rs`·`analyze.rs`).
2. 진입점을 모두 적는다. 창 메시지(`wndproc`의 WM_*), 핫키 스레드(F6/F7), 재생 스레드, 분석 스레드(`analyze_async`), 파일 열기·끌어 놓기·명령줄 인자, `player`의 pub 함수.
3. 진입점마다 상태가 바뀌는 경로를 끝까지 따라가며 아래 체크리스트를 적용한다. 바뀐 코드만 보지 말고 호출하는 쪽과 기존 테스트까지 읽는다.
4. 부분이 크면 하위 영역별로 Agent 작업자를 병렬로 띄운다. 각 작업자에게 이 체크리스트 전체와 읽기 전용 규칙을 넘긴다.
5. **반박 검증**: 발견한 항목마다 별도의 작업자에게 "이 버그가 실제로는 일어나지 않는 이유를 찾아라"고 맡긴다. 반박하지 못한 항목만 남긴다.
6. 가능하면 재현한다. OS 무관 모듈은 실패하는 단위 테스트로, 재생 엔진은 상태 전이 순서를 적은 시나리오로 보인다. Windows에서만 재현되는 것은 사용자에게 실측 절차를 넘긴다.

## 체크리스트

**A. 스레드와 상태**
- GUI 스레드, 분석 스레드, 재생 스레드, 핫키 스레드가 공유하는 상태(`STATE`, `ACTIONS`, `SEEK_US`, `STOP` 등)에서 검사 후 실행(check-then-act) 사이에 다른 스레드가 끼어들 수 있는가?
- 분석 결과의 세대 번호(`gen`)가 곡 교체·설정 변경·분석 실패 모두에서 맞게 쓰이는가? 실패하거나 다시 분석하는 중에 이전 곡의 타임라인이 재생될 수 있는가?
- 상태 기계(STOPPED/ARMED/PLAYING/PAUSED/LOST/DONE)의 모든 전이가 의도대로인가? 정지 중 탐색, 무장(armed) 중 곡 교체, 재생 끝 직후 F6 같은 순서를 따져 본다.

**B. 키 눌림 잔류**
- 재생이 멈추는 모든 경로(정지, 일시정지, 탐색, 창 전환, 곡 끝, 곡 교체, 창 닫기)에서 `release_all`이 도는가?
- 릴리스 빌드는 `panic = "abort"`다. 재생 경로에 패닉할 수 있는 `unwrap`·인덱싱·산술 오버플로가 있는가? 패닉하면 키가 눌린 채 남는다.
- 다시 시작할 때 Shift/Ctrl/페달을 타임라인이 기대하는 상태로 되돌리는가? 사용자가 실제로 누르고 있는 수식키와 겹치지 않는가?

**C. 실패를 성공으로 처리**
- `unwrap_or_default`, `.ok()`, `let _ =`로 오류를 삼키는가?
- Win32 호출(`SendInput`, 창·DC·타이머 생성, 파일 대화상자)의 반환값을 확인하는가? 실패가 사용자에게 보이는가?
- 분석이 "성공"했지만 칠 음이 없거나 일부 트랙을 읽지 못했을 때 그 사실이 화면에 보이는가?

**D. 타이밍**
- 재생 스레드 안에서 할당·잠금 대기·긴 계산을 하지 않는가?
- 대기(`wait_until`)가 정지·탐색 요청에 제때 반응하는가? 시스템 시간 변경이 아닌 단조 시계(`Instant`)를 쓰는가?
- 스케줄이 음을 원래 시각보다 허용 지연 넘게 미루지 않는가? `verify`가 이것을 실제로 검사하는가?

**E. 입력 견고성 (MIDI·경로)**
- 잘린 파일, 0 템포, 거대한 델타 타임, 수만 개의 템포 이벤트, 트랙 수 0, 형식 2 파일에서 패닉·무한 루프·과도한 메모리 사용이 없는가?
- µs 환산이 정수 오버플로 없이 긴 곡을 다루는가?
- 한글·긴 경로(260자 이상), 끌어 놓은 파일 여러 개, 확장자가 다른 파일을 다룰 수 있는가? (`DragQueryFileW` 버퍼 길이)

**F. 화면과 자원**
- DPI 변경·창 크기 0(최소화)·매우 큰 배율에서 렌더러가 패닉하거나 거대한 버퍼를 만들지 않는가?
- 타이머·GDI 객체·스레드가 창을 닫을 때 정리되는가? 종료 대기(`shutdown`)가 시간 안에 끝나지 않으면 어떻게 되는가?

## 결과 형식
항목마다 다음을 적는다.
- 등급: P1(키 눌림 잔류, 다른 프로그램에 입력, 크래시), P2(잘못된 동작, 상태 불일치, 음 누락·지연), P3(사용성)
- `파일:줄`
- 일어나는 순서를 담은 시나리오 한두 문장
- 고치는 방법 한 문장
- 재현했는지, 추론인지

마지막에 범위와 한계를 적는다. 무엇을 읽었는지, 무엇을 실행하지 않았는지(Windows 빌드, 실제 Roblox 재생 등)를 밝힌다.

## 규칙
- 감사는 읽기 전용이다. 고치는 일은 따로 한다.
- 공개 저장소다. PR 본문과 커밋 메시지에 악용 방법을 자세히 적지 않는다.
- 고칠 때는 먼저 실패하는 테스트를 쓰고, 고친 뒤 그 테스트가 통과하는지 보인다.
